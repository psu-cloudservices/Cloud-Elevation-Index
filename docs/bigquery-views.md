# Cloud Elevation Index

## BigQuery Views Guide

Step-by-step setup for the views that generate CEI scores from your billing data

> **Who this guide is for:** Higher education IT staff who have completed the [Billing Data Export Guide](billing-export.md) and now need to stand up the BigQuery views that produce CEI scores. If billing data is not yet landing in BigQuery, start with that guide first.
>
> **What this guide covers:** How to create the seven BigQuery views that turn raw billing data into CEI scores, what each view does, and how to troubleshoot when scores look off. We assume billing data for AWS, Azure, and GCP is already loaded into BigQuery; pointing the views at the right source tables is the main configuration step.

> **Note:** Views are layered. Intermediate views normalize raw billing per provider; a final CEI view computes the weighted score. Each layer can be queried independently, which makes inspection and troubleshooting straightforward at any stage. View SQL files live at [`/views`](https://github.com/psu-cloudservices/Cloud-Elevation-Index/tree/main/views) in the CEI repo.

---

## How CEI Scoring Works

CEI is a weighted score per account per billing period. Think of it like a weighted grade — each cloud service is a "subject" and its weight is determined by how much you spend on it.

1. **Total spend is calculated** for each account and billing period.
2. **Each service's share of total spend** is calculated as a percentage. If total spend is $10,000 and EC2 costs $3,000, EC2 is 30% of spend.
3. **Each service's percentage is multiplied by its CEI score** to produce a weighted score. Services that cost more and score higher contribute more positively. Services that cost a lot but score poorly pull the score down.
4. **Weighted scores are summed and divided by total percentage spend** to produce the final CEI — a single number reflecting the overall cloud maturity of the account's spend.
5. **If total spend rounds to zero** (e.g., a dormant account), CEI defaults to 0 to avoid divide-by-zero errors.

> **Worked example:** Service A (score 80, 70% of spend) and Service B (score 20, 30% of spend) → weighted scores 56 and 6 → CEI = (56 + 6) / (70 + 30) × 100 = **62**. Shifting more spend toward Service A raises the CEI; shifting toward Service B lowers it.

> **GCP credits note:** GCP billing includes credits such as committed use and sustained use discounts. The GCP pipeline subtracts these from raw cost before calculating spend percentages, so CEI reflects what was actually paid rather than the list price. Promotional credits are excluded from this subtraction to avoid artificially inflating scores.

## The Scoring Table and Versioning View

Two pieces of infrastructure must exist before any provider views can be created.

### `CEI_Scoring` table

This table stores the per-service CEI scores generated by an LLM. Every provider view joins against it to attach a score to each line of billing data.

| Field | Description |
| :---- | :---- |
| `provider` | Cloud provider (`"AWS"`, `"GCP"`, `"Azure"`) |
| `service_name` | Service identifier used to join against billing data |
| `service_alias` | Alternate service names used by third-party cost tools (repeated field) |
| `gemini_2_0_flash` | Record containing the AI-generated score and its subcomponents |

The repo ships [`cei_scores.ndjson`](https://github.com/psu-cloudservices/Cloud-Elevation-Index/blob/main/cei_scores.ndjson), a point-in-time snapshot of the dataset, and [`schema.json`](https://github.com/psu-cloudservices/Cloud-Elevation-Index/blob/main/schema.json), the table schema. You create the table from the schema and load the snapshot into it before creating any views.

> **Keep this table current:** Services missing from `CEI_Scoring` will not appear in CEI output. As new services are adopted across your accounts, refresh this table so coverage stays complete.

### `CEI_Versioned_Scores` view

This view sits on top of `CEI_Scoring` and exposes a stable, versioned interface (`provider`, `service_name`, `score_v1`). Provider views read from this view, not from `CEI_Scoring` directly, so that scoring methodology changes can ship as a new column (`score_v2`, etc.) without breaking downstream queries.

## How Billing Data Flows Through the Views

Each provider has a layered pipeline. Intermediate views shape and score billing data; the final CEI view aggregates everything into one score per account per billing period.

| Provider | Intermediate view(s) | Final view |
| :---- | :---- | :---- |
| **AWS** | `AWS_CUR_Cost_By_Service` → `AWS_Service_Scoring` | `AWS_CEI` |
| **Azure** | `Azure_Service_Scoring` | `Azure_CEI` |
| **GCP** | `GCP_Service_Scoring` | `GCP_CEI` |

Plus the shared `CEI_Versioned_Scores` view, for a total of **8 views** in the `Cloud_Elevation_Index` dataset.

> **About `FOCUS_*` views:** The repo also contains [`FOCUS_Service_Scoring.sql`](https://github.com/psu-cloudservices/Cloud-Elevation-Index/blob/main/views/FOCUS_Service_Scoring.sql) and [`FOCUS_CEI.sql`](https://github.com/psu-cloudservices/Cloud-Elevation-Index/blob/main/views/FOCUS_CEI.sql), an experimental alternative pipeline based on the [FinOps Open Cost and Usage Specification (FOCUS)](https://focus.finops.org/). This is not yet production-ready and is not covered by this guide. Stick with the per-provider views above for standing up CEI.

## Prerequisites

- Billing exports for AWS, Azure, and GCP all landing in BigQuery (see the [Billing Data Export Guide](billing-export.md))
- [Google Cloud SDK](https://cloud.google.com/sdk/docs/install) installed; authenticated with `gcloud auth login` and your project set via `gcloud config set project <your-project-id>`
- IAM permissions:
  - `roles/bigquery.dataEditor` and `roles/bigquery.jobUser` on the target `Cloud_Elevation_Index` dataset
  - `roles/bigquery.dataViewer` on all source billing datasets
- A `Cloud_Elevation_Index` dataset. Create one if it does not exist:
  ```shell
  bq mk --dataset <your-project-id>:Cloud_Elevation_Index
  ```
- The CEI repository cloned locally:
  ```shell
  git clone https://github.com/psu-cloudservices/Cloud-Elevation-Index.git
  ```

## Loading the Scoring Table

This step is shared across all providers and must happen first.

```shell
# From the root of the cloned CEI repo

# 1. Create the table from the provided schema
bq mk --table <your-project-id>:Cloud_Elevation_Index.CEI_Scoring ./schema.json

# 2. Load the seed scores
bq load --source_format=NEWLINE_DELIMITED_JSON \
  <your-project-id>:Cloud_Elevation_Index.CEI_Scoring ./cei_scores.ndjson ./schema.json

# 3. Create the versioned view that provider views will join against
bq mk --view "$(cat ./views/CEI_Versioned_Scores.sql)" \
  <your-project-id>:Cloud_Elevation_Index.CEI_Versioned_Scores
```

# AWS

Creating the views that score AWS Cost and Usage Report (CUR) data

## Overview

AWS uses three views in a chain. The first reshapes raw CUR data into a clean per-service cost summary, the second attaches CEI scores, and the third aggregates into the final account-level CEI.

## Required edits before creating views

| View file | Edit |
| :---- | :---- |
| `./views/AWS_CUR_Cost_By_Service.sql` | Update the `FROM` clause to point at your CUR billing table in BigQuery |
| `./views/AWS_Service_Scoring.sql` | No edit needed for standard CUR exports. See the third-party note below. |

> **Third-party cost tool users:** If you use a service like CloudHealth or Apptio Cloudability rather than native CUR exports, edit `AWS_Service_Scoring.sql` so the join against the scoring view uses `service_alias` instead of `service_name`. The `service_alias` field is a repeated string in `CEI_Scoring` that holds the alternate names these tools tend to emit.

## Create the views

Views must be created in order — each depends on the one before it.

```shell
bq mk --view "$(cat ./views/AWS_CUR_Cost_By_Service.sql)" \
  <your-project-id>:Cloud_Elevation_Index.AWS_CUR_Cost_By_Service

bq mk --view "$(cat ./views/AWS_Service_Scoring.sql)" \
  <your-project-id>:Cloud_Elevation_Index.AWS_Service_Scoring

bq mk --view "$(cat ./views/AWS_CEI.sql)" \
  <your-project-id>:Cloud_Elevation_Index.AWS_CEI
```

## What each view does

| View | Layer | Purpose |
| :---- | :---- | :---- |
| `AWS_CUR_Cost_By_Service` | Intermediate | Simplifies verbose CUR data into a clean cost-by-service summary per account and billing period. The only AWS view that needs to be edited for your environment. |
| `AWS_Service_Scoring` | Intermediate | Joins the simplified CUR with `CEI_Versioned_Scores` (filtered to `provider = "AWS"`) to attach a CEI score per service. **The best view to query first when troubleshooting unexpected scores.** |
| `AWS_CEI` | Final | Applies the weighted scoring logic (see "How CEI Scoring Works" above) and produces one CEI score per account per billing period, along with total cost. |

# Azure

Creating the views that score Azure consumption data

## Overview

Azure uses a two-view chain. A scoring view joins billing data against `CEI_Versioned_Scores`, and a final view aggregates into the subscription-level CEI.

## Required edits before creating views

| View file | Edit |
| :---- | :---- |
| `./views/Azure_Service_Scoring.sql` | Replace `{{Azure Data export location}}` with the fully qualified name of your Azure billing export table in BigQuery |

> **Consumption-only filter:** `Azure_Service_Scoring` filters to `price_type = "Consumption"`, which excludes reserved instance and marketplace charges so CEI focuses on on-demand usage patterns. If your institution wants reservation costs included in scoring, adjust this filter in the view file before creating it.

## Create the views

```shell
bq mk --view "$(cat ./views/Azure_Service_Scoring.sql)" \
  <your-project-id>:Cloud_Elevation_Index.Azure_Service_Scoring

bq mk --view "$(cat ./views/Azure_CEI.sql)" \
  <your-project-id>:Cloud_Elevation_Index.Azure_CEI
```

## What each view does

| View | Layer | Purpose |
| :---- | :---- | :---- |
| `Azure_Service_Scoring` | Intermediate | Reads from your Azure billing export, filters to consumption charges, and joins against `CEI_Versioned_Scores` (filtered to `provider = "Azure"`) to attach a score per service. |
| `Azure_CEI` | Final | Applies the weighted scoring logic and produces one CEI score per Azure subscription per billing period, along with total consumption cost. |

# GCP

Creating the views that score GCP billing export data

## Overview

GCP uses a two-view chain. The scoring view also calculates non-promotional credits per service so they can be subtracted from raw cost before scoring; the final view aggregates into a project-level CEI. The billing period is derived from the `invoice.month` field on the GCP billing export.

## Required edits before creating views

| View file | Edit |
| :---- | :---- |
| `./views/GCP_Service_Scoring.sql` | Replace `{{GCP BIGQUERY BILLING EXPORT}}` with the fully qualified name of your GCP billing export table in BigQuery |

> **Detailed export recommended:** Use the detailed usage cost export table (`gcp_billing_export_resource_v1_<BILLING_ACCOUNT_ID>`) rather than the standard export, since the scoring view depends on resource-level breakdowns. This matches the recommendation in the [Billing Data Export Guide](billing-export.md#gcp).

## Create the views

```shell
bq mk --view "$(cat ./views/GCP_Service_Scoring.sql)" \
  <your-project-id>:Cloud_Elevation_Index.GCP_Service_Scoring

bq mk --view "$(cat ./views/GCP_CEI.sql)" \
  <your-project-id>:Cloud_Elevation_Index.GCP_CEI
```

## What each view does

| View | Layer | Purpose |
| :---- | :---- | :---- |
| `GCP_Service_Scoring` | Intermediate | Reads from your GCP billing export, joins against `CEI_Versioned_Scores` (filtered to `provider = "GCP"`), and calculates non-promotional credits applied per service. |
| `GCP_CEI` | Final | Subtracts non-promotional credits from raw cost, then applies the weighted scoring logic to produce one CEI score per GCP project per billing period, along with total net cost. |

# Troubleshooting

## Views return no data

- Verify the source billing table reference in the view file is correct and contains data.
- Check that `CEI_Scoring` has entries for the provider in question and that `service_name` values exactly match what appears in your billing data. Casing or formatting mismatches are the most common cause of empty joins.
- Confirm IAM permissions allow read access to the source billing datasets.

## CEI scores look unexpectedly high or low

Query the intermediate `*_Service_Scoring` view to inspect per-service scores and costs before aggregation. This quickly isolates whether the issue is in the billing data or the scoring table.

```shell
bq query --use_legacy_sql=false \
  'SELECT * FROM `<your-project-id>.Cloud_Elevation_Index.AWS_Service_Scoring` LIMIT 50'
```

## "View already exists" error

Use `--force` to overwrite an existing view. Use with caution in production — the overwrite is immediate and not reversible.

```shell
bq mk --force --view "$(cat ./views/AWS_CEI.sql)" \
  <your-project-id>:Cloud_Elevation_Index.AWS_CEI
```

## Services missing from CEI output

Any service not present in `CEI_Scoring` will be silently dropped from the join and excluded from CEI calculations. If a known service is missing from output, check the scoring table first:

```shell
bq query --use_legacy_sql=false \
  'SELECT * FROM `<your-project-id>.Cloud_Elevation_Index.CEI_Scoring`
   WHERE provider = "AWS" AND service_name = "Amazon EC2"'
```

# Next Steps

## You now have CEI scores

With the views in place, `AWS_CEI`, `Azure_CEI`, and `GCP_CEI` each return one row per account (or subscription, or project) per billing period. From here you can:

- Query the final views directly for ad-hoc analysis
- Connect Looker Studio, Tableau, or another BI tool to the final views for dashboards
- Build institution-level rollups by averaging or weighting account-level scores across your organization

## Keeping the scoring table fresh

As your institution adopts new cloud services, add them to `CEI_Scoring` so they appear in CEI output. The [`cei_scores.ndjson`](https://github.com/psu-cloudservices/Cloud-Elevation-Index/blob/main/cei_scores.ndjson) file in the repo is updated periodically; you can re-load it to pick up new scores, or maintain your own additions on top.
